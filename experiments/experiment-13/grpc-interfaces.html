1. AuthorizationPDP

Unary RPC arrowhead.authz.v1 · authz-pdp :9550

Service metadata

ClientDynamicOrchestration / GRPCDecider
Port:9550 (internal) / :9650 (host)
TransportgRPC plaintext

Architecture position

Canonical PDP–PEP with three non-standard aspects.
(1) The PEP is a control-plane actor — it decides which provider addresses to disclose during service discovery, not whether to allow a connection that already exists. (2) action acts as a namespace separator ("orchestrate" vs "consume"), not an operation verb, routing requests to the correct policy set. (3) provider as a first-class XACML attribute enables per-provider IoT policies with no direct equivalent in web-service XACML. See grpc-summary.html for full analysis.

RPC: Decide

Purpose

Evaluates a single access-control request and returns PERMIT or DENY. The DynamicOrchestrator calls Decide once per provider candidate found in the ServiceRegistry. Only providers that receive PERMIT are included in the final orchestration response.

Implements XACML 3.0 Request/Response semantics over gRPC. Fail-closed: any error or non-PERMIT decision causes the provider to be excluded from results.

Two distinct action values prevent policy collision:

  • "orchestrate" — orchestration PEP; provider is set (per-provider policy evaluation)
  • "consume" — enforcement PEPs (kafka-authz, pki-rest-authz); provider is empty

Message definitions

// authorize.proto — arrowhead.authz.v1

service AuthorizationPDP {
  rpc Decide(DecisionRequest) returns (DecisionResponse);
}

message DecisionRequest {
  string domain_id = 1;  // AuthzForce domain UUID (may be empty)
  string subject   = 2;  // consumer system name  → XACML subject-id
  string service   = 3;  // service definition    → XACML resource-id
  string provider  = 4;  // provider system name  → XACML provider-id (orch only)
  string action    = 5;  // "orchestrate" | "consume"
}

message DecisionResponse {
  Decision decision    = 1;  // PERMIT | DENY | INDETERMINATE | NOT_APPLICABLE
  string   status_code = 2;  // XACML status URN (informational)
}

enum Decision {
  DECISION_UNSPECIFIED = 0;  // zero value; treat as DENY
  PERMIT               = 1;  // access granted
  DENY                 = 2;  // access denied
  INDETERMINATE        = 3;  // evaluation error; treat as DENY
  NOT_APPLICABLE       = 4;  // no policy matched; treat as DENY
}

2. CertificateLifecycle

Server-streaming arrowhead.ca.v1 · profile-ca :8089

Service metadata

Packagearrowhead.ca.v1
Serverprofile-ca (gRPC reflection enabled)
Protocore-evol/proto/certlifecycle/certlifecycle.proto
ClientPIP (Policy Information Point)
Port:8089 (internal) / :8589 (host)
TransportgRPC plaintext, server-side streaming

Architecture position

Not a PDP–PEP interface. No authorization decision is made here.
This is a CA-to-PIP attribute provisioning channel. Classic XACML has the PDP pull attributes from the PIP synchronously per request; here the model is inverted — the PIP subscribes and pre-populates its store, and enforcement PEPs query the PIP before calling the PDP. Certificate issuance and revocation events are causally coupled to authorization outcomes: a revoked certificate causes XACML DENY even if the mTLS handshake somehow passed, because cert-valid=false becomes a XACML subject attribute. See grpc-summary.html for full analysis.

grpcurl -plaintext localhost:8589 list grpcurl -plaintext localhost:8589 describe arrowhead.ca.v1.CertificateLifecycle grpcurl -plaintext -d '{"include_snapshot":true}' \ localhost:8589 arrowhead.ca.v1.CertificateLifecycle/Subscribe

RPC: Subscribe

Purpose

Opens a persistent server-side streaming RPC from profile-ca to a subscriber (PIP, audit log, or monitoring). The stream carries CertEvent messages as certificate lifecycle transitions occur — issued, revoked, expired.

When include_snapshot = true, the server first sends one SNAPSHOT event per currently-valid certificate before switching to live events. This bootstraps the subscriber from scratch without a separate REST call — critical for PIP on startup.

The stream remains open indefinitely. Subscribers run the call in a reconnect loop with exponential backoff (initial 1 s, max 30 s). Fail-closed: on disconnect the subscriber retains its last known state and does not purge its store.

Message definitions

// certlifecycle.proto — arrowhead.ca.v1

service CertificateLifecycle {
  // Subscribe opens a persistent server-side stream of CertEvents.
  rpc Subscribe(SubscribeRequest) returns (stream CertEvent);
}

message SubscribeRequest {
  // true = send SNAPSHOT events for all valid certs before live events
  bool include_snapshot = 1;
}

message CertEvent {
  string    cn         = 1;  // cert Common Name   → XACML subject-id
  string    ou         = 2;  // cert level: "lo" | "on" | "de" | "sy"
  EventType type       = 3;  // lifecycle event type
  string    issued_at  = 4;  // RFC3339; present for ISSUED/SNAPSHOT only
  string    expires_at = 5;  // RFC3339; present for ISSUED/SNAPSHOT only
}

enum EventType {
  EVENT_UNSPECIFIED = 0;  // zero value; ignore
  ISSUED            = 1;  // new cert issued     → Register(cn, ou, valid=true)
  REVOKED           = 2;  // cert revoked        → Register(cn, ou, valid=false)
  EXPIRED           = 3;  // cert expired        → Register(cn, ou, valid=false)
  SNAPSHOT          = 4;  // initial state event → Register(cn, ou, valid=true)
}
